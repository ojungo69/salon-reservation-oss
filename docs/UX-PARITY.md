# 顧客 UX の本番同等性（issue #11）

この文書は、顧客向け予約フローが本番運用の SaaS 版とユーザータスク単位でどこまで同等かを記録し、
アダプタ（issue #1）で後から差し込む前提の「意図的に無い」表面を明文化します。

## アダプタ挿入点（既定構成では描画されない）

既定のインストール（単一店舗・外部プロバイダなし）では、次の 3 つの表面は**存在しないこと**が正しい状態です。
それぞれの挿入点は予約シェルに確保済みで、`tests-browser/customer.spec.ts` の不在テストが守っています。

### 1. 店舗（location）選択

- **今の状態**: 設定は単一店舗（`locationName`）のみ。予約フローに店舗セレクタは描画されません（FR-010）。
- **挿入点**: 選択ステップ（`public/index.html` の `#journey-selection`）の先頭。複数店舗の設定モデルが
  入った時点で、サービス選択の前に店舗選択を挿入します。バックエンドの分割・トランザクション設計は
  `docs/PARITY.md` の v0.x 除外事項のとおり先行課題です。
- **不在の保証**: 既定構成で location を名乗るコントロールがないことをテストが確認します。

### 2. 本人確認（identity）アダプタ

- **今の状態**: アカウントは存在せず、予約ごとの管理キーが本人確認の代わりです。連絡先入力ステップ
  （`#journey-details`）と保存済み予約ページ（`public/bookings.html`）がその両端です。
- **挿入点**: 連絡先入力ステップの先頭（ログイン状態の表示・入力の自動補完）と、保存済み予約ページの
  エントリ（キー保管の代替）。アダプタ契約は issue #1 が先行し、LIFF/LINE を含む具体実装はここでは
  扱いません。
- **不在の保証**: 顧客ページにログイン・サインイン・友だち追加といった外部 ID 表面がないことを
  テストが確認します。

### 3. 通知（notification）チャネル

- **今の状態**: どのチャネルにも通知しません。受付結果の画面（`#booking-result`）は「運営者の確認後に
  状態が更新されます」とだけ伝え、チャネルの約束をしません。
- **挿入点**: 受付結果の画面（設定済みチャネルの案内文）と、予約状態遷移の発生源
  （`src/reservation-day.ts` の status 更新コマンド）。通知アダプタは状態遷移を購読する形で入ります。
- **不在の保証**: 既定構成の成功画面がメール・LINE・SMS などの到着を約束しないことをテストが確認します。

## ユーザータスク別 同等性マトリクス

判定は 3 値です: **同等**（本番フローと同じ結果に同じ負担で到達できる）/ **同等以上**（OSS 側だけの
価値がある）/ **先送り**（アダプタ待ち。理由を明記）。根拠列は自動テストまたは文書の所在です。

| ユーザータスク | 判定 | 根拠 |
|---|---|---|
| サービス・日時を選び、3 ステップで予約を申請する | 同等 | `tests-browser/customer.spec.ts` の一気通貫予約（320–1440 px、キーボード到達、axe） |
| 連絡先入力の前に選択内容を確かめ、その場で直す | 同等 | サマリーカードと編集リンクの往復テスト（details step の要約・編集ジャンプ・反映） |
| 送信前に完成した内容を専用画面で最終確認する | 同等 | 確認パネル（`[data-confirmation-panel]`）の表示と隔離された主ボタンのテスト |
| 多数のサービスから絞り込んで選ぶ | 同等 | 9 件カタログのキーボード操作テスト（フィルタ→選択→チップ削除、概算合計、8 件以下は従来表示のまま） |
| 選択済みサービスの合計（時間・料金）を把握する | 同等 | 概算合計行のテスト。未掲載料金が混じる場合は合計を出さない（誤読防止） |
| 空き状況をその場で更新して選び直す | 同等 | 更新ボタンのテスト（選択済み時刻を保ったまま再描画） |
| 臨時のお知らせ（短縮営業など）に気づく | 同等 | `availabilityNotice` の表示・非表示テストと設定画面の往復テスト |
| 満枠・枠切れの理由を理解して復帰する | 同等 | 上限到達文言と stale-slot 文言のシェル内テスト（選択ステップへの復帰まで） |
| 同じ日の二重予約に気づいてから申請する | 同等（同一ブラウザ内） | 保存済み予約 ≤3 件の照会→警告→確認→完了のテスト。照会失敗は申請を妨げない |
| 端末をまたいだ二重予約に気づく | 先送り | 照合は保存済み証明に限定（連絡先照合は列挙オラクル化するため不採用、research D4）。端末横断は identity アダプタ（issue #1）の領域 |
| アカウントなしで予約を確認・取消する | 同等以上 | 管理キーによる無アカウント運用（外部 ID 不要は OSS 側の特性）。保存・取消・再読込のテスト |
| 管理キーの意味を理解して保管する | 同等 | 成功画面の一文説明・コピー・保存導線のテストと `bookings.html` の入口文 |
| 予約結果の通知を受け取る | 先送り | 通知チャネルは未構成が既定。成功画面はチャネルを約束しない（不在テスト）。通知アダプタは issue #1 |
| 店舗を選ぶ | 先送り | 単一店舗モデル（`docs/PARITY.md` の v0.x 除外）。セレクタ不在テストと挿入点の文書化のみ |
| 外部 ID でログインする | 先送り | identity アダプタ待ち（issue #1）。顧客ページの外部 ID 表面不在テスト |
