# 顧客 UX の本番同等性（issue #11）

この文書は、顧客向け予約フローが本番運用の SaaS 版とユーザータスク単位でどこまで同等かを記録し、
アダプタ（issue #1）で後から差し込む前提の「意図的に無い」表面を明文化します。

## アダプタ挿入点（既定構成では描画されない）

既定のインストール（単一店舗・外部プロバイダなし）では、次の 3 つの表面は**存在しないこと**が正しい状態です。
それぞれの挿入点は予約シェルに確保済みで、`tests-browser/customer.spec.ts` の不在テストが守っています。

### 1. 店舗（location）選択

- **今の状態**: 設定は単一店舗（`locationName`）のみ。予約フローに店舗セレクタは描画されません（FR-010）。
- **挿入点**: 選択ステップ（`public/index.html` の `#journey-selection`）の先頭。複数店舗の設定モデルが
  入った時点で、サービス選択の前に店舗選択を挿入します。バックエンドの分割・トランザクション設計は
  `docs/PARITY.md` の v0.x 除外事項のとおり先行課題です。
- **不在の保証**: 既定構成で location を名乗るコントロールがないことをテストが確認します。

### 2. 本人確認（identity）アダプタ

- **今の状態**: アカウントは存在せず、予約ごとの管理キーが本人確認の代わりです。連絡先入力ステップ
  （`#journey-details`）と保存済み予約ページ（`public/bookings.html`）がその両端です。
- **挿入点**: 連絡先入力ステップの先頭（ログイン状態の表示・入力の自動補完）と、保存済み予約ページの
  エントリ（キー保管の代替）。アダプタ契約は issue #1 が先行し、LIFF/LINE を含む具体実装はここでは
  扱いません。
- **不在の保証**: 顧客ページにログイン・サインイン・友だち追加といった外部 ID 表面がないことを
  テストが確認します。

### 3. 通知（notification）チャネル

- **今の状態**: どのチャネルにも通知しません。受付結果の画面（`#booking-result`）は「運営者の確認後に
  状態が更新されます」とだけ伝え、チャネルの約束をしません。
- **挿入点**: 受付結果の画面（設定済みチャネルの案内文）と、予約状態遷移の発生源
  （`src/reservation-day.ts` の status 更新コマンド）。通知アダプタは状態遷移を購読する形で入ります。
- **不在の保証**: 既定構成の成功画面がメール・LINE・SMS などの到着を約束しないことをテストが確認します。
