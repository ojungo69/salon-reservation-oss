# Phase 0 Research: Production-Parity Roadmap and Adapter Extension Contracts

**Feature**: [spec.md](./spec.md) | **Date**: 2026-08-12 | **Method**: two independent plans (Claude Code and a Codex second-opinion planner) compared and integrated; divergences below record which side won and why.

No external-technology unknowns exist in this slice: it is documentation-only, and the roadmap deliberately stages *capabilities*, not mechanisms, so no external API surface (LINE endpoints, queueing/retry mechanisms, calendar APIs) needs verification here. Mechanism research (for example push-retry via queues versus alarms, current LIFF/ID-token verification endpoints) belongs to the stage that implements it and is recorded as an explicit prerequisite of that stage, so the roadmap never bakes in a remembered API surface.

## D1: File responsibilities — state in `PARITY.md`, order in `ROADMAP.md`, obligations in `ADAPTER-CONTRACTS.md`

**Decision**: Three documents with one responsibility each:

- `docs/PARITY.md` evolves in place into the **single state authority**: the implemented-capabilities matrix (all current rows kept: capability, public-safe implementation path, acceptance evidence), the **production-parity target matrix** beside it, the manual release checks, and the deliberate exclusions. No rename, no stub.
- `docs/ROADMAP.md` (new) holds **order only**: the versioned stage table (S0–S5) with status, delivered capabilities, prerequisites, and completion criteria. It never duplicates a capability's status — it links to the target matrix, and it carries a dedicated, prominent pointer to the authoritative exclusions record in `PARITY.md` so a reader who starts at the roadmap reaches "what is deliberately excluded from the current parity target" (reconsiderable only through a recorded revision) in one hop (the spec's US3 independent test is phrased against this link, preserving the single state authority).
- `docs/ADAPTER-CONTRACTS.md` (new) holds the **four extension contracts**.

**Rationale**: The constitution's Governance section assigns capability boundaries and deliberate exclusions to `docs/PARITY.md`; moving the target matrix or the exclusions elsewhere would contradict that assignment (or force a constitution amendment for zero gain). Readers landing on the old `PARITY.md` URL — the v0.2 release README links there — see implemented reality and the parity target side by side instead of missing the target in another file. Splitting state (what) from schedule (when) prevents the same fact living in two documents.

**Divergence record**: The initial Claude plan placed the target matrix and exclusions in `ROADMAP.md`; the Codex plan placed all state in `PARITY.md` and confined `ROADMAP.md` to ordering. Codex's layout won on the constitution-assignment argument and on old-URL reader behavior.

**Alternatives considered**: (a) everything in `PARITY.md` — three audiences in one very long file; (b) rename + pointer stub — breaks inbound-link value for nothing; (c) per-seam contract files — four places for the shared invariants to drift apart; (d) new tests/lint for document structure — violates the no-new-gates slice boundary, and review-time audits cover it.

## D2: Target-matrix row schema

**Decision**: `| Capability | Production task it serves | Status | Current evidence / remaining gap | Roadmap stage / exclusion boundary |`. `Status` is strictly one of four atomic values: `Implemented`, `Partial`, `Planned`, `Deliberately excluded` — gap descriptions and stage names never contaminate the status cell; they live in their own columns. Capability set = the union of the current implemented rows, the current exclusion rows, and issue #1's named capabilities — no invented industry-generic capabilities. Composite legacy exclusion rows — and issue #1 capabilities whose parts carry different statuses — are decomposed into atomic rows, with the decomposition visible in the matrix, so no atomic row is both planned and excluded (for example the current "Messaging, email, push, and calendar synchronization" row splits into notifications → Planned/S1, calendar synchronization → its three mode rows below, unspecified providers → Deliberately excluded).

**Assignments settled now**: identity and notifications → Planned/S1; calendar synchronization appears as **three rows matching the contract's three modes** — ICS subscription feed → Planned/S2, outbound event synchronization → Planned/S2, and inbound availability authority (external busy → fail-closed blocked slots) → **Deliberately excluded from the current target**, with the rationale and future boundary recorded in `PARITY.md` per the Governance assignment: it becomes schedulable only through a recorded roadmap revision once real demand appears and the core has a job/queue substrate (issue #1's 2026-08-11 decision) — this split keeps every Planned row's stage actually delivering that row (FR-002) and prevents S2 completion from implying an unimplemented inbound mode; staff roles → Planned/S3; multi-location → Planned/S4 (cross-day moves stay excluded — they need the separate transaction design the current table already records); import/migration → Planned/S5; external audit/event delivery → **Deliberately excluded**: nothing of the external pipeline (dispatcher, checkpointing, sink) is implemented and no stage schedules one, so the honest status is exclusion with the contract-defined seam recorded as its future boundary — claiming Partial on the strength of the *separate* implemented internal-history row would be evidence inflation (a fresh-review finding at implementation review), and adding a stage is a recorded roadmap revision. Implemented rows must not be inflated: accountless access, the operator schedule fallback, and immutable history are linked as their own implemented capabilities, never presented as evidence that external identity, notifications, or audit delivery exist.

**Rationale**: Atomic status values make the completeness audit (SC-001) mechanical; the two reference columns satisfy FR-002's every-row-references rule; the union rule keeps the matrix grounded in recorded decisions rather than speculation.

## D3: Contract document structure

**Decision**: `docs/ADAPTER-CONTRACTS.md`, one file. It opens with the shared invariants (provider-neutral core; disabled by default; unconfigured means no UI trace, no stored external identifiers, no booking-path dependency; adapters consume explicit post-commit events, every projection derives only from committed state, and a served read projection (the recorded ICS feed) must be observationally equivalent to one maintained from that event stream; booking acceptance never waits on an adapter; adapters live inside the single Worker as configuration-gated modules, never as separate deployables — constitution II and issue #1's recorded design decision). Then four seam sections — identity, notifications, calendar synchronization, audit/event delivery — each carrying the same seven-row table:

`| Dimension | Core guarantee | Adapter obligation | Operator-visible outcome |`

with rows fixed in order: Configuration gating, Event and trigger model, Failure semantics, Idempotency, Retry and terminal-failure visibility, Privacy and data minimization, Observability. No empty cells and no cells that only say "same as the shared invariants"; a short prose note under a table is allowed where a dimension needs reasoning. Seam-specific obligations live in the relevant rows:

- **Identity**: accountless booking stays the default; booking succeeds during external-identity outage; no external subject/token stored when unconfigured; link/unlink is an optional convenience (FR-006).
- **Notifications**: committed events only (acceptance, status change, reschedule — the implemented same-day move — and cancellation); duplicate-safety per event/recipient/channel; bounded retry; terminal failure visible to the operator; minimum data needed for delivery.
- **Calendar synchronization**: the contract distinguishes the three integration modes issue #1's recorded design decision (2026-08-11, issue comment) ladders them into: (1) an authenticated outbound **ICS subscription feed**, (2) **outbound event synchronization** (reservation → external event create/update/delete), and (3) **inbound availability authority** (external busy → blocked slots). The booking path never calls an external API in any mode. Fail-closed semantics apply *only* to mode 3 — an adapter explicitly configured as the inbound availability authority whose synchronized snapshot is stale/unknown/unconfirmed fail-closes the affected slots only; modes 1 and 2 never affect availability. Post-booking outbound delivery failure never rolls back acceptance and surfaces as reconciliation status (FR-005). This mode split is what reconciles fail-closed semantics with the "acceptance never waits on an adapter" invariant and with configurations that have no inbound authority at all.
- **Audit/event delivery**: the core's immutable history remains the source of truth; external delivery adds deduplication, checkpointing, gap and terminal-failure visibility, and a payload allowlist with redaction.

A closing section records the staging decision: event names and required information are described at the semantic level; TypeScript types, queue schemas, and concrete retry counts are deliberately not fixed until the first adapter stage to be implemented (S1 in the recommended order; whichever stage starts first builds the shared event delivery foundation) so the contract is proven by an implementation rather than speculative.

**Divergence record**: the initial Claude plan used prose subsections; Codex proposed the four-column table. The table won: it makes the 28-cell audit (SC-002) a row count and separates core obligations from adapter obligations from operator visibility, which prose blurs.

## D4: README parity claim

**Decision**: A short "Parity status" section: a *conditional* claim — production parity is determined by the target matrix; the current release is core-feature parity, not production parity, because target rows remain incomplete — with links to the implemented matrix, the target matrix, and the roadmap. Additionally, the existing "Deliberate limits" section's sentence listing absent capabilities ("Payments, notifications, external identity, calendar sync…are intentionally absent") is trimmed to the bounded-deployment facts plus the matrix links, because that inline list would restate capability status and go stale as stages land.

The same single-authority rule condemns two more frozen lists the initial plan had missed (both caught at plan review): `docs/RELEASING.md`'s release-notes template embeds a "currently: one location, no LINE…" limitation list — it is replaced by an instruction to derive the limitations from the target matrix at release time, with a link; and `docs/UX-PARITY.md` is reframed as a *task-level evidence view derived from* `docs/PARITY.md`: its two "`docs/PARITY.md` の v0.x 除外" references to multi-location are reworded to point at the capability's target-matrix row (which records it as planned with a stage, so "excluded" is no longer its status), and its user-task rows that carry an adapter-dependent "先送り" status (notifications, location choice, external identity) have that status column reference the corresponding target-matrix row instead of asserting status independently — the absence *evidence* in those rows stays, the status *authority* moves. A short preamble line records the derivation relationship so later stages update the target matrix and only follow references here. `CHANGELOG.md` is a historical record and is not touched.

**Rationale**: FR-007 requires wording that survives future releases; a conditional claim derived from the matrix does, a frozen list does not — and the rule applies to every document that restates capability status, not just the README.

## D5: Roadmap stages and versioning

**Decision**: `docs/ROADMAP.md` header carries `Roadmap document version: 1.0.0`, `Baseline release: 0.2.0`, the stage-status vocabulary, and a dated revision log — plus one framing sentence: every stage's completion criteria are *in addition to* the constitution's quality gates (correctness + over-implementation review, and the security review battery for security-scope changes), so no stage can read as completable on feature tests alone. Stage rows name the gate evidence their risk profile demands: S1 and S3 the security review battery, S2 and S4 conflict/isolation/reconciliation evidence, S5 dry-run, backup/rollback, and privacy evidence. No product SemVer is assigned to stages (no milestone exists to authorize one); stable stage IDs are the reference unit.

**Stage status vocabulary and transition rule**: a stage's status is exactly one of `Not started`, `In progress`, `Complete`; the only permitted edit for recording progress is changing that one status cell (plus a revision-log line), and `Complete` requires the row's completion-criteria evidence to exist — restructuring the table is a versioned revision, not a status update.

**Dependencies versus recommended order**: each stage row's Prerequisites cell separates *hard dependencies* (must exist first) from *recommended order* (priority, revisable by recorded revision). The hard dependency graph is: S0 → everything; S3 and S4 Complete → S5. Everything else — S1 before S2, S2 before S3 — is recommended order only.

Stages:

- **S0 — Documentation foundation** (this feature): both matrices, the roadmap, the 28-cell contracts, the README classification, the cross-document reference alignment (`docs/RELEASING.md` derive-from-matrix instruction, `docs/UX-PARITY.md` target-row references), and the release-allowlist registration of the two new documents. Prerequisites: none. `In progress` until every gate passes; `Complete` only after final verification.
- **S1 — Optional LINE identity and notifications**: LIFF bootstrap and login (issue #1's recorded decision fixes LIFF as the frontend surface, with an in-stage check of current LIFF versus LINE Mini App branding guidance), server-side token verification, account-link/friendship state where required, webhook raw-body signature verification, event deduplication and follow/unfollow handling, push notification queueing with retry/backoff and terminal-failure visibility. Prerequisites — hard: S0 contracts; in-stage: mechanism research (push-retry mechanism, current LIFF/token-verification endpoints). Completion: issue #1's end-to-end criteria — login verification, invalid webhook signature, duplicate webhook delivery, notification retry — all fixture-tested with **zero live LINE dependency in CI** (public repository, public CI, no channel secrets) plus the security review battery; live-channel verification is an operator-side step.
- **S2 — Calendar synchronization ladder**: the two unconditional rungs of issue #1's recorded decision — an authenticated outbound ICS subscription feed, then an optional outbound event-synchronization adapter (create/update/delete on reservation events) whose **first delivered provider is Google** (the recorded decision names it; the contract stays provider-neutral) with reconciliation visibility. Neither rung affects booking availability. **Bidirectional inbound import (external busy → fail-closed blocked slots) is deliberately *not* part of this stage or any scheduled stage**: its target-matrix row is Deliberately excluded from the current target (research D2), with the demand + job/queue-substrate condition recorded as its future boundary in `PARITY.md`; scheduling it is a recorded roadmap revision. The contract's inbound-availability-authority mode (research D3) exists so that revision has a defined seam waiting. Prerequisites — hard: S0 contracts; in-stage: the shared post-commit event delivery foundation, if it does not yet exist (whichever adapter stage starts first builds it; S1 in the recommended order); recommended: after S1 (priority only). Completion: feed and Google outbound adapter fixture-tested including duplicate/outage/reconciliation cases; no availability effect verified; the security review battery for the authenticated feed endpoint and external provider credential handling.
- **S3 — Staff and role boundary**: migration path from the single owner secret; authorization, revocation, offboarding, privacy; the accountless customer path is preserved. Prerequisites — hard: S0; in-stage: the authorization design (the current exclusions record already demands a separate authorization/migration/offboarding/privacy design before this capability). Completion: design recorded plus implementation with the security review battery.
- **S4 — Multi-location boundary**: location partitioning, transaction isolation, configuration, operator scoping. Cross-day moves are *not* implied by this stage and remain excluded pending their own transaction design. Prerequisites — hard: S0; in-stage: the partition/transaction design (the current exclusions record demands it before this capability). Completion: design recorded plus implementation with isolation/race evidence and the security review battery for the operator-scoping authorization surface.
- **S5 — Import and migration**: stable mapping, dry run, verification, idempotent resume, backup/rollback, auditability, privacy. Prerequisites — hard: **S3 and S4 Complete** — the schemas and storage paths migration writes into must be implemented and verified, not merely designed, or dry-run/idempotent-resume/rollback evidence is unproducible. Completion: dry-run, backup/rollback, and privacy evidence, plus the security review battery for external-input parsing and personal-data handling.

**Production-parity predicate** (recorded in the roadmap header and derived by the README claim): the release is production-parity when every target-matrix row is `Implemented` or `Deliberately excluded`. Completing S0–S5 does not automatically confer the claim — it is read from the matrix as it stands at that time, never from the stage table — and the claim stays honest precisely because it derives from the matrix, not from stage completion.

**Rationale for the order**: LINE is the capability issue #1 marks P0 and names first; the calendar ladder rides the same post-commit event seam once it is proven; staff/roles and multi-location are core-invariant changes rather than adapters, and they are split (unlike the initial plan's combined stage) because they carry different risk: one is an authorization design, the other a partition/transaction design — the current exclusions table already records them as separate rows. Migration is last because it hard-depends on the shapes S3/S4 settle. The recommended order is surfaced at the plan gate; the versioned revision log exists precisely so reordering is a recorded revision.

**Alternatives considered**: calendar before LINE — rejected: issue #1's P0 emphasis is LINE, and calendar does not unblock it. Combined staff+location stage (initial Claude plan) — rejected per the risk-profile split above. Product SemVer per stage — rejected: promises release numbering nobody has authorized. Bidirectional calendar import as a scheduled stage (this plan's own first draft) — rejected at plan review: it contradicts issue #1's recorded ladder decision and would promote the conditional third rung to a commitment while silently dropping the two unconditional rungs.
