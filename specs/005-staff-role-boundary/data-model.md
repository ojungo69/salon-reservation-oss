# Phase 1 Data Model: Staff and role boundary (S3)

Two pieces of stored state are added, in two different Durable Objects, both in `__`-prefixed tables
so they reach installations that already exist. Nothing already stored changes shape.

---

## 1. The roster — `InstallationConfig.__staff_roster`

```sql
CREATE TABLE IF NOT EXISTS __staff_roster (
  singleton INTEGER PRIMARY KEY CHECK (singleton = 1),
  roster_json TEXT NOT NULL
)
```

Byte-for-byte the shape of `__line_lifecycle` (`src/installation-config.ts:1613-1618`): one row, one
JSON document, created by its first write and absent until then.

**Why a JSON blob and not columns.** The roster is read whole on every resolution (R3 scans every
entry) and written whole on every command (R7's compare-and-swap needs the previous document to
compare against). There is no query this slice makes that a table of rows would serve better, and a
blob round-tripped through a parser can be validated the way `installation_state` and
`__line_lifecycle` already are: parse, re-serialise, and refuse if the bytes differ.

### `roster_json`

```jsonc
{
  "version": 1,
  "members": [
    {
      "id": "6f1c2e40-9a3b-4d17-8c5e-2b7d90a4f8e1",  // opaque, system-generated, stable forever
      "displayName": "受付 A",                // 1–80 chars, operator-chosen
      "role": "owner",                        // "owner" | "staff"
      "active": true,
      "credentialDigest": "9f86d0…",          // 64 lowercase hex, SHA-256; "" when inactive
      "createdAt": "2026-08-16T02:00:00.000Z",
      "deactivatedAt": null                   // ISO timestamp once deactivated, else null
    }
  ]
}
```

### Field rules

| Field | Rule | Requirement |
|---|---|---|
| `version` | Exactly `1`. A document with any other value is refused, not migrated. | — |
| `id` | `crypto.randomUUID()`, generated by the system, never reused, never derived from the name. The same generator every other opaque identifier in this codebase uses — reservation, closure, command, and operation ids (`src/reservation-day.ts:1919`, `2295`, `3027`; `src/installation-config.ts:1720`, `1738`). Nothing sorts staff by id, so a sortable encoding would be an encoder and a test suite bought for no reader. | FR-006, FR-015 |
| `displayName` | `boundedText(value, 1, 80)`, the repository's existing bound for operator-entered labels. Mutable. Never appears in attribution. | FR-006, FR-015 |
| `role` | `"owner"` or `"staff"`. No third value parses. | FR-002 |
| `active` | Boolean. `false` is terminal for this slice — reactivation exists, deletion does not. | FR-013 |
| `credentialDigest` | 64 lowercase hex characters while active. Set to `""` on deactivation, which is what makes the record unable to authenticate. Never the credential itself. | FR-006, FR-013 |
| `createdAt` | ISO 8601 UTC, set once. | FR-006 |
| `deactivatedAt` | `null`, or the ISO timestamp of the most recent deactivation. | FR-006 |

**No contact address, no customer link, no email.** FR-006 forbids the first; the specification's
final edge case forbids the second — a person who is both staff and customer has two unrelated
records and nothing joins them.

### Invariants enforced on every write

1. **No command takes away the last active `owner`.** A command is refused when the roster *had* a
   member with `role === "owner" && active === true` and the resulting document does not. Stated as
   a property of the *result* rather than of the operation, so role changes and record removals a
   later slice adds are covered by the same line. (FR-011)

   Note the shape carefully: it is **not** "the roster must always contain an active owner". A
   roster of staff alone is legitimate and is the likely first state — the `OWNER_TOKEN` holder
   administers the installation and adds people who are not owners. Requiring an owner-role member
   to exist would forbid creating that roster, and would then refuse to deactivate anyone in it.
   What FR-011 protects against is an installation *losing* its last in-roster owner, which is why
   the rule is about removal.
2. **Unique `id`.** Enforced at parse time, not only at creation.
3. **Digest present iff active.** `active === true` requires 64 hex characters; `active === false`
   requires `""`. A record cannot be inactive and still hold a live digest, which is what makes
   FR-010's "takes effect on the next request" structural rather than procedural.
4. **Round-trip stable.** `JSON.stringify(parse(stored)) === stored`, the same corruption check
   `#readStoredState` and `#readLineLifecycle` already apply.

### Absence is a state

An installation with no `__staff_roster` table is not a degraded installation — it is the default,
and it is the only state that exists today. `resolveActor` on such an installation answers `null`
without touching storage beyond the `sqlite_master` existence check, and `OWNER_TOKEN` remains the
only credential. (FR-017)

## 2. Attribution — `ReservationDay.__attribution`

```sql
CREATE TABLE IF NOT EXISTS __attribution (
  command_id TEXT PRIMARY KEY,
  actor_kind TEXT NOT NULL CHECK (actor_kind IN ('break_glass', 'staff')),
  actor_id   TEXT                        -- staff id, or NULL for break_glass
)
```

Three columns, because the fourth and fifth would be copies. `adapter_receipts` already carries
`operation` and `created_at` under the *same* `command_id` primary key
(`src/reservation-day.ts:1081-1088`), and every operator mutation writes both rows inside one
transaction (`#writeReceipt` at `src/reservation-day.ts:2343`, `2684`, `2892`, `3052`, `3137`), so a
receipt row is always one join away. Storing what the operation was and when it happened a second
time would only create two places for the answer to drift apart.

Created by the first operator write on a given day, through the same `CREATE TABLE IF NOT EXISTS`
inside an already-open transaction that `#ensureAdapterSchema` uses (`src/reservation-day.ts:1145`).

| Field | Rule | Requirement |
|---|---|---|
| `command_id` | The command's UUID. Primary key, so a replay cannot write a second row even if the gate were bypassed. Joins to `adapter_receipts` for the operation name and the timestamp. | FR-028 |
| `actor_kind` | `'break_glass'` when the deployment secret was used, `'staff'` otherwise. | FR-014 |
| `actor_id` | The roster `id`. `NULL` for break-glass, which has no roster record by definition. **Never the display name.** | FR-015 |

### Retention

The row lives in the day partition and dies with it, at the same purge as the reservation it
describes and the receipt it sits beside. Nobody can delete it individually — there is no route that
writes to this table other than the five mutations, and none of them delete. (FR-016)

This is a retention *statement*, not an omission, and `docs/PRIVACY.md` must carry it in those words.

### Scope

Written for the operator-initiated mutations only:

- `transitionOwner` — all six actions
- `createClosure`, `removeClosure`
- `#create` when reached through `POST /api/admin/reservations`

Not written for the public booking path or for customer cancellation — those have no operator — and
not for `#expire`, which has no actor at all.

## 3. Entities in memory

### `Actor`

The result of resolving a bearer token. Produced by `ownerGate`, consumed by the role check and by
whichever mutation follows.

```ts
type Actor =
  | { kind: "break_glass"; role: "owner" }
  | { kind: "staff"; role: "owner" | "staff"; staffId: string };
```

Note that a roster member with `role: "owner"` is an actor with owner rights but is **not**
break-glass: they are revocable, and they are the account FR-011 refuses to leave the installation
without.

### `Role` → route capability

The authoritative table is [contracts/authorization.md](./contracts/authorization.md). In this
model it is only a total function `(role, routeBucket) → allowed`, with no wildcard and no default
branch, so a route added later fails to compile rather than defaulting open.

### `StaffCredential`

Not an entity — it has no stored form. It exists as a string for the duration of one request:
generated, digested, returned once. Only `credentialDigest` persists.

## 4. State transitions

A staff member's lifecycle, all transitions owner-only:

```text
            create                    deactivate
  (absent) ─────────► active ◄──────────────────────► inactive
                        │  ▲       reactivate            │
                        │  └──────────────────────────────┘
                        │
                        └─ rotate ─► active (new digest, previous one dead on next request)
```

| Transition | Effect on the record | Refused when |
|---|---|---|
| **create** | Appends a member, `active: true`, fresh digest. Credential returned once. | The resulting document breaks any invariant in §1; or the caller is not `owner` (FR-018). |
| **rotate** | Replaces `credentialDigest` on one member. Returns the new credential once. | The member is inactive. |
| **deactivate** | `active: false`, `credentialDigest: ""`, `deactivatedAt` stamped. | It would leave zero active owners (FR-011). |
| **reactivate** | `active: true`, **a new digest is issued** — the old credential is gone and cannot be restored. | — |

Reactivation deliberately cannot resurrect the previous credential: the digest was cleared at
deactivation, which is what made revocation real. Getting the old string back would require having
kept it.

**Deletion does not exist in this slice.** FR-013 requires a deactivated record to survive so past
attribution stays resolvable, and FR-016 says attribution is not the subject's to erase. A delete
operation has to be reconciled with both before it can be designed, and the specification defers it.
